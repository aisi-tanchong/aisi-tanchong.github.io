1. 摘要

AISI（Atomized Intelligent Service Interface，原子化智能服务接口）协议旨在为AI智能体（Agent）与外部服务（Service）之间的交互提供一套标准化、模块化、可扩展的接口规范。它将传统的“复合型”API（如OpenAPI）拆解为更细粒度的“原子化”操作，使智能体能够以统一的、声明式的方式发现、理解、组合和调用服务能力，从而构建出更灵活、更强大的自动化工作流。

本协议包含四个核心组成部分：

  1. 服务描述规范：定义服务如何以结构化的JSON Schema描述其能力（即“原子操作”）。
  2. 统一调用接口：规定智能体调用服务的标准化HTTP/REST端点、请求/响应格式和错误处理机制。
  3. 动态组合机制：允许智能体根据目标，将多个原子操作按逻辑组合成一个可执行的工作流（DAG）。
  4. 状态与生命周期管理：为长时间运行的操作提供状态查询、进度跟踪和生命周期管理能力。

通过AISI协议，服务提供者可以轻松地将其功能暴露给任意兼容的AI智能体，而智能体开发者则可以像调用本地函数一样，无缝集成和编排外部服务，无需为每个服务编写特定的适配代码。

2. 动机与目标

2.1 为什么需要原子化？

当前，AI智能体在集成外部服务时面临以下挑战：

  • 接口异构性：不同服务的API设计风格、认证方式、数据格式各异，智能体需要为每个服务编写特定的解析和调用逻辑。
  • 能力过载：传统的“复合型”API（如“创建订单并支付”）将多个业务步骤捆绑在一起，智能体难以理解其内部逻辑，也无法灵活复用其中的子步骤。
  • 组合困难：智能体难以自动将不同服务的功能组合起来完成复杂任务，缺乏统一的编排标准。
  • 状态管理缺失：对于异步或长时间运行的操作，缺乏标准的状态查询和进度反馈机制。

AISI协议通过“原子化”来解决这些问题：

  • 统一描述：所有服务能力都用一致的JSON Schema描述，智能体可以“理解”每个操作的功能、输入和输出。
  • 细粒度控制：每个“原子操作”只做一件事（如“验证用户”、“计算价格”、“调用支付网关”），智能体可以按需组合。
  • 声明式组合：智能体可以通过声明式的DAG（有向无环图）来组合多个原子操作，形成可执行的工作流。
  • 内置状态管理：协议为异步操作定义了标准的状态模型和查询接口。

2.2 设计目标

  1. 标准化：为AI-服务交互提供一套业界通用的标准接口，降低集成成本。
  2. 模块化：服务能力应拆分为独立、可复用的原子操作。
  3. 可发现性：智能体应能自动发现服务的可用操作及其详细规格。
  4. 可组合性：智能体应能根据任务目标，动态组合多个原子操作形成工作流。
  5. 可观测性：提供标准化的状态跟踪、日志和错误报告机制。
  6. 向后兼容：协议应易于扩展，新版本兼容旧版本的核心交互模式。

3. 核心概念

3.1 原子操作（Atomic Operation）

原子操作是AISI协议中最基本的执行单元。它代表一个独立的、不可再分（在业务逻辑层面）的服务功能。每个原子操作必须明确声明：

  • id：唯一标识符。
  • name：人类可读的名称。
  • description：功能描述。
  • input_schema：输入参数的JSON Schema。
  • output_schema：输出结果的JSON Schema。
  • is_async：是否是异步操作。

示例： 一个“发送邮件”的原子操作，其输入是收件人、主题、正文，输出是发送成功与否的状态。

3.2 服务（Service）

服务是一组相关原子操作的集合，由一个服务提供者（Service Provider）实现和托管。服务通过一个标准的“服务描述”端点（通常是 /.well-known/aisi.json）来暴露其所有原子操作的定义。

一个服务描述至少包含：

  • service_id：服务唯一标识。
  • name：服务名称。
  • version：协议版本（如"aisi/0.1"）。
  • operations：该服务提供的原子操作列表。
  • base_url：服务调用的基础URL。

3.3 工作流（Workflow）

工作流是由智能体动态组合多个原子操作形成的有向无环图（DAG）。每个节点代表一个原子操作，边代表数据依赖关系（一个节点的输出可以作为另一个节点的输入）。

工作流本身也是一个可执行单元，可以作为一个“复合操作”被调用。AISI协议定义了工作流的描述格式（基于JSON）和标准的执行引擎接口。

3.4 智能体（Agent）

智能体是AISI协议的消费者，它能够：

  1. 发现服务：通过服务描述端点获取可用操作。
  2. 理解操作：解析input_schema和output_schema，理解如何调用。
  3. 组合工作流：根据任务目标，将多个原子操作组合成DAG。
  4. 调用执行：通过统一的调用接口触发操作或工作流的执行。
  5. 管理状态：监控异步操作的执行状态，处理结果或错误。

4. 协议规范

4.1 服务发现与描述

服务必须提供以下标准端点，供智能体发现其能力：

GET /.well-known/aisi.json

响应体必须是一个符合以下JSON Schema的“服务描述”对象：

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "AISI Service Description",
  "type": "object",
  "required": ["service_id", "name", "version", "base_url", "operations"],
  "properties": {
    "service_id": {
      "type": "string",
      "description": "服务的全局唯一标识符（建议使用反向域名格式，如 com.example.mail）"
    },
    "name": {
      "type": "string",
      "description": "人类可读的服务名称"
    },
    "description": {
      "type": "string",
      "description": "服务的详细描述（可选）"
    },
    "version": {
      "type": "string",
      "pattern": "^aisi/\\d+\\.\\d+$",
      "description": "遵循的AISI协议版本，格式为 'aisi/主版本.次版本'"
    },
    "base_url": {
      "type": "string",
      "format": "uri",
      "description": "所有操作调用的基础URL（必须以 https 开头）"
    },
    "operations": {
      "type": "array",
      "items": {
        "$ref": "#/definitions/atomic_operation"
      },
      "description": "该服务提供的原子操作列表"
    }
  },
  "definitions": {
    "atomic_operation": {
      "type": "object",
      "required": ["id", "name", "description", "input_schema", "output_schema"],
      "properties": {
        "id": {
          "type": "string",
          "description": "在服务内唯一的操作标识符（如 send_email）"
        },
        "name": {
          "type": "string",
          "description": "人类可读的操作名称"
        },
        "description": {
          "type": "string",
          "description": "操作的详细描述，说明其功能、用途和限制"
        },
        "input_schema": {
          "type": "object",
          "description": "输入参数的JSON Schema（遵循 Draft-07）。必须包含一个 'type' 为 'object' 的根节点。"
        },
        "output_schema": {
          "type": "object",
          "description": "输出结果的JSON Schema（遵循 Draft-07）。对于异步操作，这表示最终结果的格式。"
        },
        "is_async": {
          "type": "boolean",
          "default": false,
          "description": "是否为异步操作。异步操作会立即返回一个任务ID，需要通过 /tasks/{task_id} 轮询结果。"
        },
        "timeout_seconds": {
          "type": "integer",
          "minimum": 1,
          "default": 30,
          "description": "操作的超时时间（秒），仅对同步操作有效。异步操作应由服务方自行控制超时。"
        }
      }
    }
  }
}

示例响应：

{
  "service_id": "com.example.mail",
  "name": "示例邮件服务",
  "description": "提供发送电子邮件的原子化服务。",
  "version": "aisi/0.1",
  "base_url": "https://mail-service.example.com",
  "operations": [
    {
      "id": "send_email",
      "name": "发送邮件",
      "description": "向指定的收件人发送一封电子邮件。",
      "input_schema": {
        "type": "object",
        "required": ["to", "subject", "body"],
        "properties": {
          "to": {
            "type": "array",
            "items": { "type": "string", "format": "email" },
            "description": "收件人邮箱地址列表"
          },
          "subject": { "type": "string" },
          "body": { "type": "string", "contentMediaType": "text/html" }
        }
      },
      "output_schema": {
        "type": "object",
        "properties": {
          "message_id": { "type": "string" },
          "status": { "type": "string", "enum": ["sent", "queued"] }
        }
      },
      "is_async": false,
      "timeout_seconds": 10
    }
  ]
}

4.2 统一调用接口

4.2.1 调用原子操作

智能体通过向服务的 {base_url}/v1/operations/{operation_id}/execute 端点发送 POST 请求来调用一个原子操作。

请求

  • 方法：POST
  • 路径：/v1/operations/{operation_id}/execute
  • Headers：Content-Type: application/json
  • Body：一个JSON对象，其结构必须严格符合该操作 input_schema 的定义。

响应（同步操作）

  • HTTP 200 OK：操作成功执行。
    • Body：一个JSON对象，其结构符合该操作的 output_schema。
  • HTTP 202 Accepted：操作是异步的，已接受处理。
    • Body：{ "task_id": "task_123456", "status_url": "https://.../v1/tasks/task_123456" }
    • 智能体应通过 status_url 轮询任务状态。
  • HTTP 4xx：客户端错误（如输入验证失败）。
    • Body：标准错误响应格式（见4.4节）。
  • HTTP 5xx：服务端错误。

示例：调用同步的“发送邮件”操作

请求

POST /v1/operations/send_email/execute HTTP/1.1
Host: mail-service.example.com
Content-Type: application/json

{
  "to": ["user@example.com"],
  "subject": "测试邮件",
  "body": "这是一封来自AISI协议的测试邮件。"
}

响应

HTTP/1.1 200 OK
Content-Type: application/json

{
  "message_id": "msg_20231027120000",
  "status": "sent"
}

4.2.2 异步操作与任务管理

对于标记为 is_async: true 的操作，调用后会返回 202 Accepted 和一个任务ID。智能体通过以下接口查询任务状态和结果：

GET {base_url}/v1/tasks/{task_id}

响应

  • HTTP 200 OK：任务存在。
    • Body：
    {
  "task_id": "task_123456",
  "status": "pending|running|succeeded|failed|cancelled",
  "result": { ... }, // 仅当 status 为 succeeded 时存在，符合 output_schema
  "error": { ... },  // 仅当 status 为 failed 时存在，符合标准错误格式
  "progress": 0.65,  // 可选，进度指示 (0-1)
  "created_at": "2023-10-27T12:00:00Z",
  "updated_at": "2023-10-27T12:00:05Z"
}
  • HTTP 404 Not Found：任务不存在。

4.3 工作流组合与执行

4.3.1 工作流描述格式

工作流使用一个JSON对象来描述，它定义了节点（操作）和边（数据流）。

{
  "workflow_id": "order_fulfillment",
  "name": "订单履约工作流",
  "description": "从创建订单到发货的完整流程。",
  "version": "1.0",
  "nodes": [
    {
      "node_id": "create_order",
      "operation": {
        "service_id": "com.example.shop",
        "operation_id": "create_order"
      },
      "inputs": {
        "user_id": "{{workflow.input.user_id}}",
        "items": "{{workflow.input.items}}"
      }
    },
    {
      "node_id": "process_payment",
      "operation": {
        "service_id": "com.example.payment",
        "operation_id": "charge_card"
      },
      "inputs": {
        "order_id": "{{nodes.create_order.output.order_id}}",
        "amount": "{{nodes.create_order.output.total_amount}}"
      }
    }
  ],
  "output": {
    "order_id": "{{nodes.create_order.output.order_id}}",
    "payment_status": "{{nodes.process_payment.output.status}}"
  }
}

关键字段说明：

  • nodes：工作流节点列表，每个节点引用一个特定的原子操作（通过 service_id 和 operation_id）。
  • inputs：节点的输入映射。使用 JSON模板字符串 引用其他节点的输出（格式如 {{nodes..output.}}）或工作流的初始输入（{{workflow.input.}}）。
  • output：工作流的最终输出，同样使用模板引用节点输出。

4.3.2 工作流执行

智能体可以将工作流描述提交给一个支持工作流执行的“工作流引擎”（可以是独立的服务，或由某个服务提供者托管）。

POST {workflow_engine_url}/v1/workflows/execute

  • Body：包含 workflow（工作流描述）和 input（初始输入数据）。
  • 响应：与调用原子操作类似，返回 200（同步）或 202（异步）以及结果或任务ID。

4.4 错误处理

所有错误响应应使用统一的JSON格式：

{
  "error": {
    "code": "validation_failed",
    "message": "输入数据验证失败。",
    "details": [
      {
        "field": "to",
        "issue": "必须是一个有效的邮箱地址。"
      }
    ]
  }
}

标准错误码（部分示例）：

  • invalid_input：输入不符合schema。
  • operation_not_found：操作不存在。
  • service_unavailable：服务暂时不可用。
  • task_not_found：异步任务不存在。
  • workflow_execution_failed：工作流执行失败。

5. 安全与认证

服务提供者必须实施适当的安全措施：

  1. HTTPS：所有通信必须使用TLS 1.2或更高版本加密。
  2. 认证与授权：服务应支持标准的认证机制（如OAuth 2.0、API Key）。认证方式应在服务描述中声明（可通过扩展字段）。
  3. 输入验证与清理：服务必须严格按照 input_schema 验证所有输入，防止注入攻击。
  4. 速率限制：建议对API调用实施速率限制，并在响应头中提供配额信息（如 X-RateLimit-Limit, X-RateLimit-Remaining）。

6. 扩展性

协议可通过以下机制扩展：

  1. 自定义操作属性：在原子操作描述中添加非标准的 x-* 字段。
  2. 服务元数据：在服务描述中添加 metadata 字段，存放供应商特定信息。
  3. 协议版本：通过 version 字段管理兼容性。

7. 示例应用场景

场景1：智能客服工单自动处理

  1. 服务：工单系统、邮件服务、用户数据库、知识库。
  2. 原子操作：create_ticket, find_user, search_knowledge_base, send_email。
  3. 工作流：
    1. 接收用户问题。
    2. find_user 获取用户信息。
    3. search_knowledge_base 尝试自动回答。
    4. 如果找到答案，send_email 回复用户并 create_ticket 记录（状态为“已解决”）。
    5. 如果未找到答案，create_ticket 分配人工客服。

场景2：电商订单自动化

  1. 服务：商品目录、购物车、支付网关、库存管理、物流。
  2. 原子操作：check_inventory, calculate_tax, charge_payment, update_inventory, create_shipment。
  3. 工作流：
    1. 用户提交订单。
    2. check_inventory 验证库存。
    3. calculate_tax 计算税费。
    4. charge_payment 扣款。
    5. 支付成功后，并行执行：update_inventory 扣减库存，create_shipment 生成运单。

C. 与其他规范的关系

  • OpenAPI：AISI可以视为对OpenAPI的“原子化”补充。一个传统的OpenAPI接口可以被拆分为多个AISI原子操作。
  • JSON Schema：AISI重度依赖JSON Schema作为数据描述和验证的标准。
  • W3C WebAssembly：未来可能将原子操作编译为WASM模块，实现跨平台、沙箱化执行。
