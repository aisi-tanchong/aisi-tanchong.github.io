1. 摘要

AISI（Atomized Intelligent Service Interface，原子化智能服务接口）协议旨在为人工智能体（AI Agent）与真实世界服务之间，建立一套机器可读、语义无歧义的标准化描述与交互接口。其核心目标是将任意复杂的商业或生活服务，拆解、描述为最小可执行单元——"原子服务"，使智能体能够像人类理解菜单一样，精准发现、推荐并调用这些服务。

本协议定义了服务提供方如何描述其"原子服务"，以及智能体如何发现、理解与调用这些服务的基础数据框架与交互范式。它不依赖任何特定平台，旨在成为开放、中立的服务互联网"基础语法"。

2. 愿景与原则

2.1 愿景

构建一个以用户意图为中心、由智能体作为主要交互界面的下一代服务互联网。在这个网络中，服务如同信息一样自由、高效地流动，用户通过自然语言即可无缝获取全球服务。

2.2 核心原则

  1. 机器可读性优先：描述格式的首要目标是确保AI能无歧义地理解。
  2. 原子化：服务应被描述为最小、不可再分且可独立交付的单元。
  3. 语义标准化：对关键概念（如时间、地点、价格）采用公认的标准格式。
  4. 平台中立与开放性：协议本身不绑定任何特定商业平台，鼓励广泛实现。
  5. 渐进演化：协议版本应保持向后兼容，并通过社区共识持续演进。

3. 核心概念定义

原子服务 (Atomic Service)
能够被独立提供、交付并完成一次完整价值交换的最小服务单元。例如："一杯外送至指定地址的350毫升冰美式咖啡"是一个原子服务，而"开一家咖啡馆"不是。
服务提供方 (Provider)
发布并履行原子服务的实体或个人。
智能体 (AI Agent)
代表用户，能够理解意图、发现并调用原子服务的软件实体。
服务描述 (Service Description)
按照本协议格式编写的，对一个原子服务的完整定义文件。
服务注册表 (Service Registry)
存储并可被查询的服务描述集合，可以是中心化索引或去中心化网络。

4. 协议数据架构

一个完整的AISI服务描述是一个JSON对象，其根结构如下：

{
  "aisi_version": "0.1",
  "metadata": {...},
  "service_unit": {...},
  "atomic_description": {...},
  "fulfillment_terms": {...},
  "provider_info": {...}
}

4.1 metadata - 元数据

用于标识和追踪服务描述本身。

字段 类型 必填 描述 示例
service_id 字符串 是 服务的全局唯一标识符。推荐格式：provider_domain:service_type:unique_id "coffee.example.com:latte:basic_01"
language 字符串 是 描述文本使用的语言代码。 "zh-CN"
created_at 字符串 是 描述创建时间（ISO 8601）。 "2024-06-01T10:00:00+08:00"
updated_at 字符串 是 描述最后更新时间（ISO 8601）。 "2024-06-10T15:30:00+08:00"
status 字符串 是 服务状态。枚举："draft", "published", "suspended", "archived" "published"

4.2 service_unit - 服务单元

对人类和智能体展示的核心信息。

字段 类型 必填 描述 示例
name 字符串 是 服务的简洁、人类可读名称。 "经典拿铁咖啡（外送）"
category 字符串数组 是 服务分类标签，用于高效检索。 ["餐饮", "咖啡", "外送"]
human_description 字符串 是 面向人类的详细服务说明。 "一款由意式浓缩咖啡与蒸煮牛奶调和而成的经典咖啡饮品，口感顺滑。"
tags 字符串数组 否 额外的关键词标签。 ["新品", "招牌", "提神"]

4.3 atomic_description - 原子化描述（协议核心）

从机器视角，无歧义地定义服务的"输入"与"输出"。

字段 类型 必填 描述 示例
input 对象 是 执行此服务所需的输入参数。 见下文 input 结构详述。
output 对象 是 服务方承诺交付的确定结果。 见下文 output 结构详述。

4.3.1 input 对象结构

定义用户或智能体需要提供什么。

字段 类型 必填 描述 示例
parameters 数组 否 可选的定制化参数列表。 见下文参数表示例。
constraints 对象 否 执行服务的必要前提条件。 {"delivery_address": {"required": true}}

parameters 数组中的参数项示例：

{
  "name": "杯型",
  "key": "size",
  "type": "select",
  "required": true,
  "options": [
    {"value": "medium", "label": "中杯 (350ml)", "price_effect": 0},
    {"value": "large", "label": "大杯 (500ml)", "price_effect": 5}
  ]
}

4.3.2 output 对象结构

定义服务方承诺交付什么。

字段 类型 必填 描述 示例
core_item 字符串 是 交付物的最核心描述。 "1杯拿铁咖啡"
specifications 对象 否 具体的规格属性。 {"volume_ml": 350, "temperature": "热"}
material_list 字符串数组 否 主要材料或成分列表。 ["意式浓缩咖啡", "蒸煮牛奶"]

4.4 fulfillment_terms - 履约条款

定义服务如何、何时、何地被交付。

字段 类型 必填 描述 示例
pricing 对象 是 价格信息。 {"base_price": 30.00, "currency": "CNY"}
location 对象 是 服务提供的地理范围。 见下文位置对象示例。
timing 对象 是 服务时间相关信息。 见下文时间对象示例。

位置对象示例：

{
  "type": "delivery_circle",
  "address": "北京市海淀区XX路XX号",
  "coordinates": {"latitude": 39.9042, "longitude": 116.4074},
  "radius_meters": 1500
}

时间对象示例：

{
  "preparation_duration_minutes": 5,
  "estimated_duration_minutes": 25,
  "business_hours": [{"days": ["Mon", "Tue", "Wed", "Thu", "Fri"], "open": "08:00", "close": "20:00"}]
}

4.5 provider_info - 提供方信息

字段 类型 必填 描述 示例
id 字符串 是 提供方唯一标识。 "starbucks_financial_park"
name 字符串 是 提供方公开名称。 "星巴克（金融街店）"
contact 对象 否 用于履约联系的公开信息。 {"phone": "13800138000"}

5. 服务发现与调用接口（参考性）

注意：本章节描述了基于上述描述的建议性交互流程，并非强制标准。

5.1 服务发现

智能体通过查询服务注册表来发现服务。注册表应提供API，支持基于以下条件的过滤：

  • category 和 tags
  • 地理位置（如：在某个坐标的半径内）
  • price 范围
  • timing （如：当前是否在营业时间内）

5.2 服务调用

  1. 订单创建：智能体代表用户，按照服务描述的input结构组装参数，向提供方的接单端点发起请求。
  2. 订单确认：提供方返回订单ID和支付信息（如适用）。
  3. 状态同步：提供方应通过Webhook或状态查询API，向智能体同步订单状态（如：accepted、preparing、delivering、completed）。

附录B：标准化字段格式

  • 日期与时间：必须使用 ISO 8601 格式。
  • 地理坐标：采用WGS-84坐标系，longitude（经度）在前，latitude（纬度）在后。
  • 货币代码：采用 ISO 4217 三位字母代码。
